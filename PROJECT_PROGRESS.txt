⚠ تعليمات لأي مساعد ذكاء اصطناعي يفتح هذا الملف في محادثة جديدة:
هذا مشروع طويل مقسّم على خطوات صغيرة جدًا بالاتفاق الصريح مع صاحب
المشروع. القواعد الثابتة لطريقة العمل (لا تتغير بدون طلب صريح جديد):

1. كل خطوة = تغيير صغير ومحدد فقط (ملف واحد أو مكوّن واحد أو شاشة
   واحدة)، ليست دفعة كبيرة من التغييرات.
2. بعد تنفيذ الخطوة: تُسلَّم "الملف كامل" (أرشيف/zip لكامل مشروع
   RasidAccountingSystem بعد التعديل، جاهز يُفتح في Visual Studio).
3. بعد التسليم مباشرة: تتوقف ولا تكمل، وتشرح للمستخدم "الخطوة الجاية
   هتعمل فيها إيه بالظبط" بدون تنفيذها.
4. لا تنفّذ الخطوة الجاية إلا بعد موافقة صريحة من المستخدم على وصفها.
5. بعد كل موافقة وتنفيذ: حدّث هذا الملف بنفس الأسلوب (سجل الخطوة اللي
   خلصت + اقتراح الخطوة الجاية) قبل ما ترسل الرد النهائي للمستخدم.
6. بيئة التنفيذ الحالية Linux بدون Visual Studio/.NET Desktop Runtime/
   NuGet — التحقق الوحيد المتاح آليًا هو: صحة XML/XAML + عدم كسر أي
   Reference موجود في csproj. الـBuild والاختبار البصري الفعلي يقوم
   بيه المستخدم في Visual Studio عنده، ويبلّغ بأي خطأ لإصلاحه فورًا.
7. لا تحذف أو تعيد كتابة أي جدول/خدمة/شاشة محاسبية موجودة فعليًا —
   فقط أضف عليها (انظر قسم "قرارات تصميمية" تحت).

الحالة الحالية بالظبط: خطوة 5 (الهيكل العام: Sidebar+Header+Content
Placeholder) — منفّذة ومُسلَّمة، في انتظار موافقة المستخدم البصرية +
وصف الخطوة 6.

1) البنية التقنية الفعلية (تم فحصها من الكود الحقيقي)
---------------------------------------------------------------------

- قاعدة البيانات: SQLite محلي (System.Data.SQLite.Core)، بدون ORM — استعلامات
  SQL مباشرة عبر Services/DatabaseService.cs و DatabaseExecutor.cs و
  DatabaseConnectionManager.cs (إدارة اتصالات + إعادة محاولة عند القفل).
- مكتبات مهمة: MahApps.Metro (عناصر واجهة)، LiveCharts/LiveCharts.Wpf
  (رسوم بيانية)، iTextSharp (PDF)، EPPlus + ClosedXML (Excel)،
  BouncyCastle (تشفير قاعدة البيانات - DatabaseEncryptionHelper.cs).
- نظام ترخيص مدمج: LicenseService.cs + جدول SystemLicense + LicenseAuditLog.
- نظام صلاحيات مستخدمين: PermissionService.cs + Users + UserPermissions +
  UserSessions + PermissionsManagementView.

5) عناصر قابلة لإعادة الاستخدام مباشرة (مؤكدة من الكود، مش تخمين)
---------------------------------------------------------------------
- طبقة قاعدة البيانات كاملة (DatabaseConnectionManager/DatabaseExecutor):
  آمنة للتزامن (WAL + Semaphore + Retry)، تصلح كما هي كأساس لأي جداول
  جديدة (Cars, WorkOrders, Technicians...).
- Customers + CustomerTransactions + CustomerBalanceSummary: أساس مباشر
  لقسم "العملاء" المطلوب (بيانات العميل + رصيد + كشف حساب موجودين
  فعليًا)، ينقصه فقط الربط بجدول Cars الجديد.
- Products/StoreInventory/InventoryTransactions: أساس مباشر لقسم
  "المخزن" المطلوب (كود صنف، رصيد، حد أدنى، صرف/إضافة) — يحتاج فقط
  ربط حركة الصرف بأمر الشغل الجديد بدل فاتورة البيع فقط.
- SalesInvoice(Items) + PaymentVouchers/ReceiptVouchers + Treasury: أساس
  مباشر لقسم "الفواتير" و"الحسابات" و"صافي الربح" المطلوب.
- PermissionService/Users: أساس لصلاحيات "الفنيين" كمستخدمين بصلاحية
  محدودة، بدل نظام صلاحيات منفصل.
- SmartSearchComboBox: قابل للتطوير مباشرة ليصبح "البحث السريع" الشامل
  (عميل → سيارة → أمر شغل → فواتير) المطلوب في القسم 14.
- BackupService, Logger, MessageBoxService, CurrencyHelper: أدوات عامة
  تصلح لأي دومين، لا تحتاج تعديل جوهري.

6) مشاكل/مخاطر مكتشفة يجب التعامل معها أثناء التنفيذ
---------------------------------------------------------------------
- لا يوجد أي مفهوم "سيارة" مرتبطة بعميل → يحتاج تصميم جدول Cars +
  علاقة Customers(1)-Cars(N) + مفتاح خارجي في كل الجداول الجديدة
  (WorkOrders) بدل تعديل الجداول القديمة نفسها (لتفادي كسر الفواتير
  والحسابات الحالية).
- لا يوجد مفهوم "أمر شغل" كحالة تسبق الفاتورة → WorkOrders لازم يكون
  جدول جديد مستقل، والفاتورة (SalesInvoice) تُنشأ من أمر الشغل عند
  التسليم (ربط WorkOrderId اختياري في SalesInvoices) بدل استبدال نظام
  الفواتير الحالي.
- تعدد التصنيفات المحاسبية الحالية (شيكات/أقساط/عهدة/بنوك) أعقد بكثير
  مما تحتاجه ورشة سيارات صغيرة/متوسطة فعليًا — القرار المقترح: تبقى
  موجودة في قسم "الحسابات" كخيارات متقدمة، لكن الشاشة الرئيسية
  ("الحسابات" في طلبك) تعرض فقط الأرقام العملية (فواتير، مقبوضات،
  مصروفات، أرصدة، صندوق) وتُخفي التعقيد الزائد خلف تبويبات فرعية.
- بيئة التنفيذ الحالية (هذه المحادثة): بيئة Linux معزولة بدون Visual
  Studio ولا .NET Framework Desktop Runtime ولا وصول لـ NuGet
  (nuget.org غير متاح من الشبكة المسموح بها هنا) ولا واجهة رسومية.
  → لا يمكن فعليًا تنفيذ "dotnet build/run + اختبار بصري" من هذه البيئة
  كما هو مطلوب حرفيًا في خطة التنفيذ. الحل العملي: كل مرحلة تُسلَّم
  كملفات كود/XAML جاهزة + شرح دقيق للتغييرات، ويقوم صاحب المشروع
  بعمل Build/Run فعلي على جهازه في Visual Studio بعد كل مرحلة، ويبلّغني
  بأي خطأ Compile أو سلوك غير متوقع لإصلاحه فورًا قبل الانتقال للمرحلة
  التالية. هذا التزام كامل بروح "اختبر بعد كل مرحلة" المطلوبة، لكن
  بتوزيع أدوار مختلف عن التنفيذ الآلي الكامل.
